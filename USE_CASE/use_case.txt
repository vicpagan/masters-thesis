>The paper mentions three "analyses/visualizations" that can be performed
> (poincar plots, heat load, and diffusion), and gives a description of the
> algorithms used. What I have a hard time finding in the paper is, for any
> of those (all would be great of course), some notion of the computational
> complexity. That is, given the size of the input data, how long does the
> computation take. These could be just measured times for different input
> sizes, or some big-O complexity measure perhaps.

The computational complexity of the heat load and diffusion analyses are
low, where in this case by low I mean they take significantly less time to
a complete than a simulation time step. The simulation time steps were ~
100 seconds, and those calculations ~ 1 second (depending on whats
counted). Thats part of whats in Figure 4: in the Calculation red and blue
bars those are computation times.

The heat load is using escaped particles (from the simulation volume) so
thats a small fraction of the total number of them escaping per step,
meaning the data size is relatively small - at least to begin with, but it
grows over time, aggregating over escaped particles across time. I dont
have exact numbers at my fingertips, but we worked in the limit where a
single Summit node sufficed, and where about 1TB was the upper limit
estimate for the kinds of simulations. The load gets rebalanced among
multiple ranks, thats what the rebalance time is.

The diffusion data uses a few quantities on a 3D mesh, where the mesh needs
to fit into the memory of a single node. So, its up to 10s of GBs per
simulation time step.

The Poincare plots use similar sized data to the diffusion analysis are
much more expensive than the other plots computational: using a single GPU,
around 100s of seconds. There are times for that in Figure 3.


> For these analyses/visualizations, given the input data size what is the
> output data size? Or is the output so small it doesn't really matter?

Apart from whats coming from the simulation, the head load and diffusion
ones didnt generate appreciable extra output data. On the Poincar maps, it
generates puncture tracks, which I think were GBs per time step. The plots
are what the scientists actually look at though, which are just images, so
those track files are debatably intermediaries.


> For any of these analyses/visualizations, are there any options to
> compute for less time and obtain lower-quality output? For instance,
> running half the iteration would shorten the execution time by half, but
> introduce error in the output while remaining useful.

On the Poincar: yes, the resolution is adjustable. Figure 3 is timing for
different choices made. The example in Figure 7 would have fewer punctures
to measure from if the resolution were reduced.

On the other analyses, there isnt really the option to do something like
this. Its just determined by the simulation.


> For any of these analyses/visualizations, when executed in parallel is
> there any data about the parallel speedup or parallel efficiency achieved?
> I see some weak scaling experiments in the paper, but have a hard time
> inferring from these some parallel performance model. Perhaps they are all
> very nicely parallel, if implemented correctly, and parallel efficiency is
> always high?

We didnt do any assessment of how well the analyses parallelized as such.
The Poincare mapping was always single GPU each (though with multiple
running concurrently to the simulation). And the others were always the
same fixed number of MPI ranks/threads.


> The paper mentions that the first step of the workflow can apply
> compression/refactoring, which can introduce error (e.g., via lossy
> compression). Is there any information about the effect of the
> analyses/visualizations. That is, if an analyses is given data with error
> e, then its output will have error e'? Perhaps e' is higher than e? I
> realize this is a vague question, but because the notion of error is
> application-specific I am not sure how to ask it in a more concrete manner.

We didnt do any assessment of that; but as a group, were interested in that
in lossy compression and errors in quantities of interest (QoIs) further
downstream. e' would indeed have a different (possibly much larger) error. I
dont know if any of these specific analyses are the best suited, since none
of the data is much larger than about a TB max. But in general,
collaborators (e.g. Qian Gong) have been looking into preserving conserved
quantities and guaranteed bounds on QoIs.
